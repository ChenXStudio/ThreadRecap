# Codex thread writeback feasibility

## Decision

**GO** for implementing ThreadRecap on the stable Codex app-server API.

The feasibility gate passed with Codex CLI `0.144.2`: a real non-ephemeral CLI
session was located from its hook `session_id`, resumed as the same thread, and
received a new turn through `turn/start`. The server emitted the matching
`turn/completed`, and `thread/read` showed the user marker and agent result in
that same persisted turn.

This is a narrow feasibility result. It does not claim that the later cooldown
state machine or its recursive-trigger guard is already implemented.

## Supported surface used

The probe followed the current official Codex manual and the JSON schema
generated by the tested CLI version. It used only:

- hook input fields documented for `SessionStart`, `UserPromptSubmit`, and
  `Stop`;
- app-server JSONL `initialize` / `initialized`;
- `thread/list`, `thread/resume`, `turn/start`, `turn/completed`, and
  `thread/read`;
- stable `clientUserMessageId`, persisted as the user message `clientId`.

It did not enable `experimentalApi`, automate a UI, or read an unpublished
database. The manual explicitly says the transcript format is not stable, so
the probe checked only file presence and write completion, not transcript
contents or structure.

## Real hook probe

A temporary ignored marketplace copy was installed through the normal plugin
marketplace flow. Only that copy received the probe `hook_entry.py`; the
repository's production hooks configuration and future Task 8 entry point were
not changed. The vetted copy was exercised with:

```text
codex exec --dangerously-bypass-hook-trust --sandbox read-only --json <benign prompt>
```

No approvals-and-sandbox bypass was used. The command created a persisted
thread and completed normally.

The three captured records belonged to one session and had these sanitized
observations:

| Event | `session_id` | `turn_id` | `transcript_path` | `cwd` | Event-specific |
| --- | --- | --- | --- | --- | --- |
| `SessionStart` | string, UUID-shaped | absent | string | string | `source` was `startup` |
| `UserPromptSubmit` | string, UUID-shaped | string, UUID-shaped | string | string | event name matched |
| `Stop` | string, UUID-shaped | string, UUID-shaped | string | string | transcript existed, was nonempty, and ended with a newline |

Every record also contained a string capture timestamp. Recursive scanning
confirmed that fields named for tokens, keys, authorization, cookies, or
secrets held only the redaction placeholder. No real prompt, identifier,
transcript, path, credential, or captured JSONL is included in this report.

## Real app-server probe

The probe accepted an explicit `--codex` binary and also supports normal PATH
discovery; no machine-specific executable path is stored in the repository.
Using the captured session ID, the stable JSONL flow completed within its
bounded timeout with all checks true:

```text
initialized=true
session_thread_mapping=true
thread_id_matches_session_id=true
non_ephemeral=true
resumed_same_thread=true
turn_completed=true
internal_client_id_persisted=true
result_in_marked_turn=true
```

The submitted visible input was:

```text
⏱ 会话已冷却，使用 $thread-recap 生成阶段摘要
```

`turn/start.clientUserMessageId` used a `thread-recap-internal:` prefix.
`thread/read` persisted that value as `userMessage.clientId`; the corresponding
completed turn also contained an agent message. This gives the later state
machine a stable field for identifying an internally generated turn and a
stable turn boundary for associating its result.

## Failure modes and remaining work

- A missing, ambiguous, ephemeral, or differently resumed thread is a NO-GO.
- A missing matching `turn/completed`, missing persisted client ID, or missing
  result in the marked turn is a NO-GO.
- app-server startup and model work can be slow; the probe uses a bounded
  timeout and reports sanitized error codes.
- The real CLI run observed unrelated local MCP startup timeout warnings, but
  the target turn completed and the stable protocol checks passed.
- The app-server writeback process did not add a second set of records to the
  temporary hook capture file. Therefore Task 8 must still verify the complete
  recursive-trigger behavior with the real cooldown state machine; this report
  proves the stable marker and writeback mechanism, not the finished guard.
